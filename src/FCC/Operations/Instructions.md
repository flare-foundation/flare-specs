# Instructions

A TEE machine executes [actions](Actions.md) prepared by its [TEE proxy](../TeeManagement/TeeProxy.md).
Each action is built from one of two upstream payloads:

- A [_TEE instruction_](#tee-instructions) — a signed off-chain payload from a [relay client](RelayClient.md), originating from an on-chain [_instruction event_](#instruction-events). The proxy assembles an action once signed copies meet the [voting](Voting.md) thresholds.
- A [_direct instruction_](#direct-instructions) — a minimal payload (`opType`, `opCommand`, `message`) submitted by an authorized client or generated by the proxy itself. Direct instructions bypass the event flow and voting.

## Instruction Events

A [user](../../Terminology/Roles.md#user) issues an instruction by calling the extension's [_instructions sender_](../Extensions/Overview.md#extension-data-structure) contract on Flare.
The instructions sender calls the `FlareTeeManager` contract, which validates the caller and emits a [`TeeInstructionsSent`](../Types/Abi/Events/TeeExtensionRegistry.md#teeinstructionssent) event.
The caller must be either the extension's registered instructions sender or a governance-registered system instructions sender; the latter is required for [system operations](../Extensions/Overview.md#system-vs-custom-extensions) (`F_` op-type prefix).

### Thresholds

A TEE proxy forwards an instruction only when data provider signatures meet the [voting](Voting.md) threshold by combined weight under the current signing policy.
The threshold defaults to the signing policy's own threshold, constrained on-chain to $\geq 50\%$.
[`F_FDC2 PROVE`](../Commands/F_FDC2--PROVE.md) is the only command for which the proxy reads a per-instruction override (`thresholdBIPS` in its FDC2 request header).

### Cosigners

The event's `cosigners` and `cosignersThreshold` fields let the issuing contract impose an additional multisig requirement.
When `cosigners` is non-empty, the proxy also waits for at least `cosignersThreshold` signatures from those addresses.

A weighted majority of malicious data providers could strip the cosigner fields and bypass enforcement at the proxy.
Each extension that uses cosigners is responsible for its own mitigation; see [Cosigner Enforcement](Actions.md#cosigner-enforcement).

## TEE Instructions

A _TEE instruction_ is the off-chain payload that data providers and cosigners submit to a TEE proxy in response to an instruction event.
The event's `teeMachines` field carries one [`TeeMachine`](../Types/Abi/TeeMachine.md#teemachine) record per destination; senders produce and submit one TEE instruction per record, copying the record's `teeId` into the instruction.

The wire envelope is the [`Instruction`](../Types/Wire/Instruction.md#instruction) JSON body posted at [`POST /instruction`](../TeeManagement/TeeProxy.md#external-write-apis):

- `data` — the [`Data`](../Types/Wire/Instruction.md#data) payload: every field of the [`TeeInstruction`](../Types/Abi/Instruction.md#teeinstruction) ABI struct plus `additionalVariableMessage`.
- `signature` — produced by the sender over [`HashForSigning(data)`](#signature-format).

The signature covers `teeId`, so a compromised proxy cannot replay an instruction to a different machine.

### Augmentation

The instruction carries two fields the sender may populate per command:

- `additionalFixedMessage` lies inside `TeeInstruction`, is part of [`instructionHash`](#signature-format), and must be identical across all senders contributing to the same vote.
- `additionalVariableMessage` lies alongside `TeeInstruction` in `data`, is hashed and signed separately, and may differ per sender.

Two system commands populate them via a per-command procedure run by the [relay client](RelayClient.md):

- [`F_FDC2 PROVE`](../Commands/F_FDC2--PROVE.md#augmentation-procedure)
- [`F_WALLET KEY_DATA_PROVIDER_RESTORE`](../Commands/F_WALLET--KEY_DATA_PROVIDER_RESTORE.md#augmentation-procedure)

All other instructions — including every custom-extension instruction — are signed and relayed with both fields empty.

### Signature Format

`instructionHash` is the keccak-256 hash of the ABI-encoded [`TeeInstruction`](../Types/Abi/Instruction.md#teeinstruction) struct (which excludes `additionalVariableMessage`).
The hash that gets signed is

$$
\mathrm{HashForSigning} = \mathrm{Hash}(\mathrm{instructionHash},\ \mathrm{Hash}(\mathrm{additionalVariableMessage})).
$$

The final ECDSA signature is produced from $\mathrm{HashForSigning}$ following the [Ethereum Signed Message](../../Utilities/Signing.md) procedure.

The proxy uses `instructionHash` to match votes from different signers on the same instruction.
`instructionId`, by contrast, is the event index from the smart contract; it identifies the originating event but does not bind the variable per-sender content.

## Direct Instructions

A _direct instruction_ skips data provider voting and dispatches straight to a TEE machine via the proxy's [direct queue](../TeeManagement/TeeProxy.md#processing-queues).
The wire payload is the [`DirectInstruction`](../Types/Wire/Instruction.md#directinstruction) JSON body. Direct instructions enter the proxy via two paths:

- _External_: clients submit to `POST /direct`, an endpoint optionally enabled per deployment.
  When enabled, the proxy authenticates requests with an `X-API-Key` header by default.
  The endpoint rejects any operation in the system (`F_`) namespace; it is intended for custom-extension operations.
- _Proxy-initiated_: the proxy issues direct instructions for system services:
  - [`TEE_INFO`](../Commands/F_GET--TEE_INFO.md) — liveness and state polling.
  - [`INITIALIZE_POLICY`](../Commands/F_POLICY--INITIALIZE_POLICY.md) — on proxy startup.
  - [`UPDATE_POLICY`](../Commands/F_POLICY--UPDATE_POLICY.md) — when the proxy observes a new signing policy on-chain.
